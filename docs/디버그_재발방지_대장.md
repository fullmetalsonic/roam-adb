### BUG-2026-001 — Windows TLS 인증서 private key 지속 실패

- 발견일: 2026-08-24
- 심각도: HIGH
- 상태: CLOSED

#### 증상·재현

Gateway register/auth 통합시험에서 TLS 연결이 예상치 못한 EOF로 끝났고 서버 진단에 Windows 플랫폼이 ephemeral key를 지원하지 않는다는 암호화 예외가 나타났다.

#### 직접 원인·증거

생성한 self-signed 인증서를 CurrentUser 저장소에 넣는 과정에서 Windows SChannel이 재사용할 수 있는 지속 private key 연결이 보장되지 않았다. 인증서 복사본에는 `HasPrivateKey`가 기대와 다르게 동작했다.

#### 수정·재발방지

인증서를 메모리 PFX로 내보내 `UserKeySet | PersistKeySet`으로 다시 로드한 뒤 저장하고 PFX byte 배열을 즉시 zero 처리했다. TLS 지문 불일치, 등록, 정상·공격자 인증 통합시험을 자동 실행한다.

#### 재시험

- BUILD: PASS, 경고 0·오류 0
- INTEGRATION: PASS

### BUG-2026-002 — 한글 작업경로 Gradle test worker 실패

- 상태: CLOSED

Kotlin 시험 class가 실제 생성됐지만 `ClassNotFoundException: GatewayProfileTest`가 발생했다. Android Gradle의 non-ASCII 검사 해제만으로는 JVM test worker 문제가 해결되지 않았다.

소스와 APK 출력은 원래 위치에 두고, pure JVM `core-model` 빌드 출력만 가장 가까운 ASCII 상위 경로의 `.roamadb-build/<path-key>`로 이동했다. Gradle Wrapper 전체 검증에 `test`를 포함했다.

#### 재시험

- `:core-model:test --rerun-tasks`: PASS 3/3
- `test assembleDebug lintDebug`: PASS

### BUG-2026-003 — 인증 제한시간이 정상 세션까지 종료

- 발견일: 2026-08-24
- 심각도: HIGH
- 상태: CLOSED

#### 증상·재현

코드 리뷰에서 TLS·로그인용 15초 token이 인증 후 session read loop에도 그대로 전달되는 것을 확인했다. 장시간 원격 디버깅이 15초 뒤 끊길 수 있었다.

#### 직접 원인·수정

인증 단계와 인증 완료 session의 CancellationToken을 분리했다. 세션은 Gateway 전체 종료 또는 사용자 연결 종료에만 취소된다.

#### 자동 재발방지·재시험

인증 제한시간을 500ms로 둔 뒤 정상 인증하고 750ms 후 같은 세션으로 ping하는 시험을 추가했다. non-loopback listener 거부 시험을 포함한 Gateway 전체 시험 PASS 9/9.

### BUG-2026-005 — READY/PC_CONNECTED 의미와 취소 경쟁

- 발견일: 2026-08-24
- 심각도: MEDIUM
- 상태: CLOSED(코드), 실기기 회귀 필요

#### 증상·원인

Gateway TLS 인증만 성공해도 `PC_CONNECTED`로 표시했으며, 사용자가 OFF한 뒤 blocking 연결이 늦게 반환하면 이전 작업이 ERROR 또는 성공 상태를 덮을 가능성이 있었다.

#### 수정

인증된 tunnel 준비는 `READY`로 표시하고 실제 ADB stream 연결 전에는 `PC_CONNECTED`를 사용하지 않는다. 작업 세대 ID를 도입해 OFF·재시작 이전의 성공/실패 결과를 폐기하고 늦게 열린 session을 닫는다.

#### 재시험

- Android build/test/lint: PASS
- 실제 네트워크 지연 중 OFF: 현장 검증 필요

### BUG-2026-007 — relay 시작 응답 제한시간 누락

- 발견일: 2026-08-24
- 심각도: MEDIUM
- 상태: CLOSED

#### 증상·직접 원인

독립 코드 리뷰에서 Gateway가 PC loopback ADB client를 받은 뒤 휴대폰의 `relay_ready`를 세션 종료까지 기다리는 것을 확인했다. 인증된 휴대폰이 고장 나거나 악의적으로 응답하지 않으면 PC socket과 relay port를 계속 점유할 수 있었다.

#### 수정·자동 재발방지

`relay_start` 뒤 `relay_ready`에는 인증 제한시간과 같은 길이의 별도 linked timeout을 적용했다. 시험에서는 300ms 제한으로 인증·relay 게시·PC 접속까지 수행한 다음 휴대폰이 준비 응답을 보내지 않도록 하고, 2초 안에 PC socket read가 EOF 0을 반환하는지 확인한다.

#### 재시험

- Gateway build: PASS, 경고 0·오류 0
- Gateway 전체 자동시험: PASS 11/11
- stalled relay local socket 종료: PASS

### BUG-2026-008 — Android 인증 제한시간이 PC 대기 relay에 잔존

- 발견일: 2026-08-24
- 심각도: HIGH
- 상태: CLOSED(코드), 실기기 회귀 필요

#### 증상·직접 원인

독립 코드 리뷰에서 Android `SSLSocket.soTimeout=15초`가 Gateway 인증과 relay 게시 뒤에도 유지되는 것을 확인했다. 사용자가 ON을 누른 뒤 PC에서 15초 안에 `adb connect`를 실행하지 않으면 `relay_start` 대기 read가 시간초과되고 relay가 1.5초 간격으로 재게시될 수 있었다.

#### 수정

TLS handshake, 등록, 인증과 `relay_published` 응답까지만 15초 제한을 사용한다. 인증된 relay가 Gateway loopback에 게시된 직후 Android socket read timeout을 0으로 바꿔 사용자의 PC 접속을 기다리는 동안 끊기지 않게 했다. PC가 접속한 뒤 휴대폰 local adbd 연결에는 별도의 5초 제한을 유지한다.

#### 재시험

- Android `test assembleDebug lintDebug`: PASS
- 실제 Fold8에서 15초 이상 READY 대기 뒤 PC 접속: 현장 검증 필요

### BUG-2026-009 — 연결 모드 RowScope import로 Compose compile 실패

- 발견일: 2026-08-25
- 심각도: LOW
- 상태: CLOSED

#### 증상·재현

3개 연결 방법 UI를 추가한 첫 전체 Android 빌드에서 debug와 release Kotlin compile이 모두 `RowColumnParentData?.weight` 내부 접근 오류로 실패했다.

#### 직접 원인·확인 증거

`Modifier.weight`는 `Row` 수신 범위에서 쓰는 API인데 잘못된 top-level import가 내부 심볼로 해석됐다. 문제 import를 제거한 뒤 같은 `Row` 안의 `Modifier.weight(1f)`가 정상 compile됐다.

#### 수정·재발방지·재시험

잘못된 import만 제거하고 RowScope 호출은 유지했다. 이후 옵션 행 전체에 접근성 `selectable`을 적용했다. `test assembleDebug lintDebug` 전체 재실행 PASS로 debug/release Kotlin compile과 APK assemble을 함께 검증했다.

### BUG-2026-010 — runtime 모듈 단독 Lint의 네트워크 권한 계약 누락

- 발견일: 2026-08-25
- 심각도: LOW
- 상태: CLOSED

#### 증상·재현

컴파일 수정 뒤 전체 Lint에서 `AndroidNetworkRouteChecker`의 `ConnectivityManager.activeNetwork` 호출에 `MissingPermission` 오류 2건이 발생했다.

#### 직접 원인·확인 증거

최종 app manifest에는 `ACCESS_NETWORK_STATE`가 있었지만 해당 API를 소유한 `runtime` Android library manifest에는 선언이 없었다. 병합 앱은 권한을 가졌어도 라이브러리 단독 Lint가 자체 권한 계약을 확인할 수 없었다.

#### 수정·재발방지·재시험

`runtime/src/main/AndroidManifest.xml`에도 `ACCESS_NETWORK_STATE`를 선언했다. 권한은 정상 권한이며 사용자 승인 창을 만들지 않는다. 전체 모듈 `lintDebug`를 다시 실행해 오류 0건, 의존성 새 버전 안내만 남음을 확인했다.

### BUG-2026-011 — 사전검사 오류 뒤 Foreground Service·타일 상태 잔존

- 발견일: 2026-08-25
- 심각도: MEDIUM
- 상태: CLOSED(코드), 실기기 회귀 필요

#### 증상·재현

코드 리뷰에서 Tailscale 미연결 등으로 `ConnectionController.start()`가 `ERROR`로 전환해도 `RoamAdbService`가 계속 foreground에 남고, 타일이 클릭 직후의 ON 표시를 유지할 수 있음을 확인했다.

#### 직접 원인·영향 범위

서비스는 사용자 STOP 명령이나 Android의 서비스 종료 때만 foreground를 내렸다. 연결 상태 Flow의 비실행 오류를 관찰하지 않아 앱 본문은 오류·OFF 버튼 상태인데 알림과 타일은 ON처럼 보이는 불일치가 생길 수 있었다. VPN 사전검사, ADB 포트 누락과 최초 Gateway 접속 실패가 영향을 받는다.

#### 수정·재발방지·재시험

서비스 전용 main coroutine scope에서 연결 상태를 관찰한다. 사용자가 START한 뒤 상태가 비실행으로 바뀌면 foreground 알림을 제거하고 서비스를 종료하며 `TileService.requestListeningState`로 타일을 새로고침한다. 오류로 자체 종료할 때는 `onDestroy`가 `stop()`을 다시 호출해 오류를 OFF로 덮지 않도록 최종 상태를 보존하고, 사용자 STOP 때만 정상 OFF로 전환한다. Android `test assembleDebug lintDebug` PASS. 실제 Fold8 알림·타일 동기화는 현장 검증 필요다.

### BUG-2026-012 — CI 호환 JDK 탐색이 기존 JAVA_HOME 17을 허용

- 발견일: 2026-08-25
- 심각도: LOW
- 상태: CLOSED

#### 증상·재현

GitHub 공개 직전 회귀시험에서 Gateway는 13/13 PASS했지만 Android 빌드가 `languageVersion=21` 도구체인을 찾지 못해 중단됐다. PC에는 JDK 21이 설치돼 있었지만 프로세스의 `JAVA_HOME`은 JDK 17을 가리키고 있었다.

#### 직접 원인·확인 증거

CI에서 설정한 JDK를 재사용하도록 빌드 스크립트를 일반화하면서 `JAVA_HOME/bin/java.exe` 존재만 확인하고 실제 주 버전을 검사하지 않았다. 따라서 유효한 JDK 17 경로를 JDK 21로 잘못 인정했다.

#### 수정·자동 재발방지·재시험

`JAVA_HOME/release`의 `JAVA_VERSION`이 21인지 먼저 검사하고, 그렇지 않으면 설치된 Microsoft JDK 21을 선택하도록 수정했다. 같은 공개 후보에서 `test assembleDebug lintDebug`를 다시 실행해 BUILD SUCCESSFUL과 동일 APK SHA-256을 확인했다. GitHub Actions의 Windows Android job도 Temurin 21을 명시해 이 스크립트를 그대로 실행한다.

`v0.1.0-spike` EXE를 더블클릭하면 콘솔이 잠깐 나타난 뒤 종료돼 코드·QR·상태를 볼 수 없었다. 최초 기획과 구현 전 승인안에는 일반 사용자용 버튼 UI, QR/6자리 코드, 진단·연결·해제가 포함돼 있었다.

#### 직접 원인·잘못된 기존 접근

Gateway 프로토콜 스파이크의 CLI를 공개 다운로드 산출물로 그대로 사용하면서 요구사항-릴리스 대조와 더블클릭 사용자 흐름 검증을 생략했다. CLI 내부 기능 통과를 제품 UI 완료로 잘못 확대 해석했다.

#### 수정·자동 재발방지·재시험

WPF `RoamADB Gateway`를 별도 모듈로 추가하고 상태, 시작/정지, 2분 코드, QR, 지문, ADB 작업, 등록 기기 해제를 화면에 배치했다. `v0.1.1_요구사항_재감사.md`에서 릴리스 완료 조건을 명시했다. 실제 창을 실행해 Tailscale 주소 표시, 코드·QR 생성과 중지 시 폐기를 확인했다.

### BUG-2026-014 — WPF 단일 파일 배포본의 네이티브 DLL 누락

- 발견일: 2026-08-25
- 심각도: HIGH
- 상태: CLOSED(설치본·Portable 재시험 PASS)

#### 증상·재현

프레임워크 의존 Release EXE는 열렸지만 Inno Setup으로 설치한 self-contained 단일 EXE는 창을 만들지 못하고 종료됐다. Windows Application 로그에 `.NET Runtime 1026`, `System.DllNotFoundException`, `SetWindowLongPtrWndProc`가 기록됐다.

#### 직접 원인·영향 범위

`PublishSingleFile=true`만 지정하고 WPF가 사용하는 네이티브 라이브러리의 자체 추출 옵션을 넣지 않았다. Portable과 설치본 모두 영향을 받았다.

#### 수정·자동 재발방지·재시험

게시 스크립트에 `IncludeNativeLibrariesForSelfExtract=true`를 추가했다. 이후 완료 조건에 공개 후보 Portable과 설치본의 실제 창 생성 시험을 모두 포함한다.

동일 옵션으로 다시 게시하고 silent 설치한 EXE를 실제 실행했다. GUI 창이 정상 생성·유지됐고 새 `.NET Runtime` 또는 `Application Error` 이벤트가 없었다. 설치본과 Portable은 같은 게시 EXE 바이트를 사용한다.

### BUG-2026-015 — 종료 이벤트 안의 재귀 Close 호출로 crash

- 발견일: 2026-08-25
- 심각도: MEDIUM
- 상태: CLOSED(정상 종료·이벤트 로그 재시험 PASS)

#### 증상·재현

Gateway가 꺼진 상태에서 닫기 단추를 누르면 창은 사라졌지만 Application 로그에 `InvalidOperationException: 창을 닫는 중에는 ... Close ... 호출할 수 없습니다`가 기록됐다.

#### 직접 원인

비동기 `Closing` 이벤트에서 첫 닫기를 취소한 뒤 정리가 즉시 끝나는 경우, 같은 닫기 호출 스택 안에서 `Close()`를 다시 호출했다.

#### 수정·자동 재발방지·재시험

종료 시작 상태를 별도로 두고 첫 이벤트는 항상 취소한다. Gateway 정리 뒤 `DispatcherPriority.ApplicationIdle`에 두 번째 닫기를 예약해 최초 닫기 이벤트가 완전히 반환된 다음 실행한다. 재시험은 정상 종료 코드와 새 Application Error 부재를 함께 확인한다.

설치본 GUI를 열고 일반 닫기 단추로 종료했다. 프로세스가 남지 않았고 종료 시각 이후 Windows Application 로그에 새 오류가 없었다. 이어서 silent uninstall도 exit code 0으로 완료됐다.

### BUG-2026-016 — 두 번째 실행 프로세스가 소유하지 않은 mutex 해제 시도

- 발견일: 2026-08-25
- 심각도: MEDIUM
- 상태: CLOSED(중복 실행 실제 재시험 PASS)

#### 증상·원인

독립 코드 리뷰에서 이미 실행 중인 경우에도 `OnExit`가 무조건 `ReleaseMutex()`를 호출하는 경로를 확인했다. 두 번째 프로세스는 기존 mutex를 소유하지 않으므로 안내창을 닫은 뒤 `ApplicationException`이 발생할 수 있었다.

#### 수정·자동 재발방지·재시험

mutex를 실제로 새로 만든 첫 프로세스만 `_ownsSingleInstance=true`로 표시하고 소유 프로세스만 해제하도록 수정했다. 설치본 첫 창을 유지한 채 같은 EXE를 두 번째로 실행해 “이미 실행 중” 안내를 확인하고 닫았다. 두 번째 프로세스는 종료되고 첫 창만 남았으며, 두 PID 모두 정상 종료한 뒤 새 `.NET Runtime`·`Application Error` 이벤트가 0건임을 확인했다.

## 7. 반복 실패 규칙

- 원인을 확인하지 않은 추측성 수정을 약 5회 이상 반복하지 않는다.
- 같은 실패가 반복되면 증상, 재현, 확인 사실, 시도, 실패 이유와 다음 실험을 먼저 정리한다.
- 브라우저·앱·소스가 다르면 작업경로, 설치 APK 버전, 실행 프로세스와 실제 제공 소스를 확인한다.
- 현장 검증이 필요한 문제는 PASS가 아니라 `현장 검증 필요`로 표시한다.
