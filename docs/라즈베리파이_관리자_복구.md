# Raspberry Pi 관리자 유지보수 권한 복구

## 1. 문제와 해결 상태

2026-09-01 감사 수정 중 `roamadb` 계정의 중복 `NOPASSWD: ALL`을 제거했다. 제거 전 `passwd -S roamadb`를 확인하지 않았고, 수정 뒤 확인 결과 계정 상태는 `L`(password locked)이었다. 당시 SSH 공개키 로그인과 RoamADB 기능은 정상이었지만 일반 `sudo`에 입력할 수 있는 유효한 비밀번호가 없었다.

복구 전 영향은 다음과 같았다.

- USB ADB, 자동 USB 테더링, Tailscale과 공개키 SSH: 정상
- 안전 종료: 현재 설치된 제한 명령으로 가능
- `apt full-upgrade`, 새 root 설정 변경: 관리자 복구 전 불가
- 데이터 손실: 확인되지 않음

2026-09-01 실기기 복구와 전체 업그레이드·재부팅까지 완료했다. 비밀번호를 추측하거나 전체 무암호 sudo를 영구 복원하지 않았다. 사용자가 Windows의 비공개 입력창에서 새 비밀번호를 직접 정했고, SHA-512 crypt 해시만 SD에 임시 저장했다. one-shot 복구 payload가 계정 비밀번호를 활성화하고 root 소유의 고정 유지보수 명령을 설치한 뒤 임시 해시를 삭제했다.

## 2. 복구가 설치하는 권한

`scripts/recover-locked-pi-admin.sh`는 다음 한 명령만 무암호 sudo로 허용한다.

```text
/usr/local/sbin/roamadb-maintain
```

이 root 소유 wrapper는 인수를 정확히 하나만 받고 다음 세 동작만 허용한다.

- `update`: Debian 패키지 목록과 전체 업그레이드
- `reboot`: 정상 재부팅
- `poweroff`: 파일시스템을 동기화한 뒤 정상 종료

임의 명령, 임의 파일 경로와 추가 인수는 거부한다.

## 3. 실기기 복구 절차

2026-09-01 Zero 2 W에서 실제 통과한 절차다. 각 단계 결과를 확인하고 다음 단계로 진행한다.

1. PC에서 `scripts/roamadb-pi-poweroff.ps1`을 실행한다.
2. Tailscale ping과 SSH가 응답하지 않는 것을 확인한 뒤 전원과 휴대폰 USB를 분리한다. 초록 ACT LED는 전원 공급 중 남을 수 있으므로 단독 판정 기준으로 쓰지 않는다.
3. microSD를 Windows 카드리더에 넣고 `bootfs` 파티션을 연다.
4. Windows에서 bootfs 드라이브 문자를 직접 확인한 뒤 비공개 터미널에서 다음 도구를 실행한다. 예시는 `E:`이며 실제 문자로 바꾼다. 새 비밀번호를 두 번 입력하면 `bootfs/roamadb-password.hash`가 생성되고 평문은 저장하지 않는다.

```powershell
.\scripts\set-pi-recovery-password.ps1 -BootDrive E:\
```
5. `scripts/recover-locked-pi-admin.sh`를 bootfs 최상위에 같은 파일명으로 복사한다.
6. `cmdline.txt` 원본을 별도 파일로 백업한다. 기존 한 줄 끝에 다음 세 항목을 공백으로 구분해 추가한다.

```text
systemd.unit=kernel-command-line.target systemd.run=/boot/firmware/recover-locked-pi-admin.sh systemd.run_success_action=poweroff
```

7. `cmdline.txt`를 한 줄 형식으로 유지하고 SD를 안전하게 제거한다.
8. SD를 Pi에 장착하고 `PWR IN` 전원을 연결한다. 복구 payload가 root로 한 번 실행된 뒤 Pi가 자동으로 종료돼야 한다.
9. 최대 2분 기다린 뒤 전원을 뺐다가 10초 후 다시 연결해 정상 부팅한다. LED만으로 복구 성공을 확정하지 않는다.
10. PC에서 공개키 SSH가 복구됐는지 확인하고 `passwd -S roamadb`가 `P`인지 확인한다.
11. 다음 명령을 실행해 일반 sudo에는 새 비밀번호가 필요하고, 무암호 허용 범위는 고정 maintenance·safe-poweroff wrapper뿐인지 확인한다.

```sh
sudo -n -l
sudo -n /usr/bin/id -u
sudo -n /usr/local/sbin/roamadb-maintain update
```

12. 업데이트 후 다음 명령으로 정상 재부팅한다.

```sh
sudo -n /usr/local/sbin/roamadb-maintain reboot
```

13. 재부팅 뒤 Tailscale, SSH, USB 테더링, `adb devices -l`, loopback `5037`, 방화벽, 부팅 오류와 파일시스템 오류를 다시 확인한다.

복구 payload는 계정 상태가 `P`로 바뀐 것을 확인한 다음 `roamadb-password.hash`를 삭제하고, `cmdline.txt`에서 자기 실행 인수 세 개를 제거한다. bootfs에 `.done` 파일이 생성돼야 한다. 임시 해시가 남았거나 인수가 제거되지 않았으면 전원 재인가를 반복하지 말고 SD를 PC에 다시 연결해 원본 `cmdline.txt`를 복원한다.

### 3.1 실제 결과와 첫 시도 실패

첫 시도는 `systemd.run`과 `systemd.run_success_action`만 넣었다. OS의 영구 기본 대상 `multi-user.target`이 generator가 만든 `default.target`보다 우선되어 `kernel-command-line.service`는 생성됐지만 시작되지 않았다. 실제 증거는 `ConditionResult=no`, 실행 시각 없음, journal 항목 없음, 계정 `L`, `.done` 없음과 임시 해시 잔존이었다.

`systemd.unit=kernel-command-line.target`을 추가한 두 번째 시도에서 복구가 실행됐다. 정상 부팅 뒤 다음 결과를 확인했다.

- `passwd -S roamadb`: `P`
- `roamadb-password.hash`: 삭제됨
- `recover-locked-pi-admin.sh.done`: 생성됨
- `cmdline.txt`: 복구 인수 세 개 모두 제거됨
- 일반 명령 `sudo -n`: 비밀번호 요구로 거부됨
- `roamadb-maintain update`: 95개 업그레이드·8개 신규 설치, 종료 코드 0
- `roamadb-maintain reboot`: 정상 재부팅
- 재부팅 커널: `6.18.39+rpt-rpi-v8`
- 업그레이드 잔여: 0, 실패 systemd unit: 0
- SSH·Tailscale·ADB·선행 SSH 방화벽 service: 모두 active·enabled
- 새 커널 실제 Fold8 회귀: USB ADB `device`, `rndis,adb`, USB 인터넷 HTTP 204, 52바이트 합성 파일 SHA-256 왕복 일치

## 4. 재발 방지

- 설치 스크립트는 OS 업그레이드를 권한 축소보다 먼저 실행한다.
- 비밀번호가 잠긴 headless appliance에는 전체 sudo 대신 root 소유의 고정 maintenance wrapper를 먼저 설치한다.
- 권한 축소 전후에 `passwd -S`, `sudo -n -l`, SSH 새 세션과 필요한 유지보수 명령을 별도로 시험한다.
- 안전 종료·복구 경로를 실제 통과하기 전에는 감사 항목을 CLOSED 또는 PASS로 표시하지 않는다.
