# RoamADB — 기술 아키텍처

## 1. 문서 상태

- 상태: 3차 기존 Tailscale 경유·ADB 전용 스파이크 구현 + `portable-usb-bridge` 목표안 승인
- 구현·빌드: Android APK와 Windows Gateway 인증·raw relay·정확한 tailnet listener 빌드 성공
- 기준 플랫폼: Samsung Android 16(API 36) 이상
- 기준 기기: Galaxy Z Fold8, Android 17, One UI 9
- PC 우선 플랫폼: Windows 11

실제 구현 범위와 시험 결과는 `구현_현황_2026-08-25.md`와 `릴리스_v0.1.2-spike.md`를 기준으로 한다. 휴대형 브리지의 상세 계약은 `휴대형_USB_ADB_브리지_기획서.md`를 기준으로 하며 부품 도착 전까지 목표 설계다.

## 2. 아키텍처 목표

- 휴대폰에는 단일 APK만 설치한다.
- 직접 PC tunnel과 선택적 Tailscale 공급자를 모듈로 분리하고 휴대폰의 로컬 무선 ADB TCP 엔드포인트를 안전하게 중계한다.
- 사용자가 요청할 때만 선택한 보안 연결과 ADB relay를 실행한다.
- 집 PC에서는 표준 ADB와 개발 도구를 최대한 그대로 사용한다.
- ADB가 일반 LAN·공용 네트워크에 직접 노출되지 않도록 한다.
- 오픈소스 원본과 자체 코드를 모듈 경계로 분리한다.
- Android 무선 디버깅의 Wi-Fi 전제조건이 맞지 않는 사용자를 위해 USB ADB와 휴대형 Linux bridge를 별도 transport로 제공할 수 있게 한다.
- 기존 무선 경로와 휴대형 USB 경로의 구현·상태·검증 결과를 섞어 표시하지 않는다.

### 3.1 계획된 휴대형 USB 브리지 구조

```text
┌──────────────── Fold8 ─────────────────────────────┐
│ LTE/5G + 2.4 GHz hotspot                           │
│ USB debugging / adbd                               │
│ Wireless debugging OFF                             │
└──────────── Wi-Fi ───────────┬──── USB device ─────┘
                               │
                               ▼
┌──────────── Raspberry Pi Zero 2 W ─────────────────┐
│ Wi-Fi client / Tailscale node                      │
│ USB host / adb client-server                       │
│ SSH or planned RoamADB Bridge Agent                │
└───────────────────┬────────────────────────────────┘
                    │ Tailscale restricted path
                    ▼
┌──────────────── Windows 집 PC ─────────────────────┐
│ SSH / adb client / Codex / Android Studio / scrcpy │
└────────────────────────────────────────────────────┘
```

이 경로에서 Fold8의 Tailscale 앱과 RoamADB Android relay는 데이터 전달의 필수 구성요소가 아니다. 브리지 자체가 Tailscale node이며 Fold8에는 표준 USB ADB RSA 승인만 요구한다. 초기 스파이크는 SSH 안에서 브리지 `adb`를 실행하고, PC 표준 도구 통합은 loopback SSH forwarding을 검증한 뒤 Bridge Agent 여부를 결정한다.

네트워크 공급자는 모듈 경계로 분리한다. 현재 앱에는 세 가지 선택이 보인다.

- `direct-home-server`: 집 PC Helper의 TLS/QUIC 서버로 직접 연결 — 실험적, 공인망 listener 미구현
- `embedded-secure-network`: 앱에 사설망 엔진을 넣는 원툴 경로 — 계획, 실행 차단
- `existing-vpn-adb-only`: 공식 Tailscale 앱을 먼저 연결하고 RoamADB는 인증·ADB relay만 수행 — 현재 권장·구현
- `portable-usb-bridge`: Fold8 핫스팟과 USB ADB를 사용하는 외부 Linux bridge — 계획 승인, 하드웨어 대기

직접 PC 서버 모드는 Tailscale 제어 평면을 사용하지 않지만 공인 IPv4 포트포워딩 또는 외부 접근 가능한 IPv6가 필요하다.

## 4. 기반 소스 전략

### 4.1 Tailscale 모드 기반 후보

현재 스파이크는 libtailscale을 반입하지 않고 외부 공식 Tailscale 앱의 VPN 경로를 재사용한다. RoamADB는 `VpnService`를 실행하지 않으며 Android 기본 네트워크가 VPN transport인지 확인한 다음 일반 TLS socket으로 PC Tailscale 주소에 접속한다. PC Gateway는 `tailscale ip -4`가 반환한 정확한 주소에만 bind한다.

아래 내용은 후속 내장형 원툴 모드의 목표 설계다.

Tailscale 모드를 구현할 때는 Tailscale Android 저장소를 기반 애플리케이션으로 포크하고 ADB 기능을 독립 모듈로 추가하는 방식을 검토한다. 직접 PC 서버를 1차 모드로 선택하면 provider-neutral Android 앱에 필요한 libtailscale 모듈만 선택적으로 결합하는 구조를 우선한다.

이유:

- VPN 생명주기, 로그인, 네트워크 전환과 Android `VpnService`가 이미 구현되어 있다.
- `libtailscale`은 Go 코어를 `gomobile bind`로 Android AAR에 묶는 공식 구조다.
- ADB 기능을 추가하는 쪽이 완성된 VPN 생명주기를 LADB 앱으로 옮기는 것보다 위험이 낮을 가능성이 크다.

최종 선택은 승인 후 두 upstream을 고정 커밋으로 체크아웃하고 빌드 구조를 비교한 뒤 확정한다.

### 4.2 ADB 구현 결정 — 표준 ADB를 투명 중계

AOSP 문서는 무선 디버깅의 페어링 서버와 ADB TLS 서버가 각각 TCP 포트에서 동작하며 PC가 `adb pair HOST:PORT`, `adb connect HOST:PORT`로 접속한다고 명시한다. LADB 원본도 일반 Android 앱 안에서 발견한 포트에 `adb connect localhost:<port>`를 사용한다.

따라서 RoamADB는 native ADB 서버나 ADB 프로토콜을 앱에 포함하지 않는다.

1. 휴대폰 앱이 자기 `127.0.0.1:<무선 ADB 포트>`에 일반 TCP socket으로 접속한다.
2. 앱과 Gateway의 인증된 TLS session이 raw byte를 변경 없이 전달한다.
3. 집 PC의 공식 `adb.exe`가 Gateway loopback 포트에 접속한다.
4. ADB Wi-Fi pairing, RSA key와 ADB TLS는 PC `adb.exe`와 Android `adbd`가 그대로 담당한다.

참고 원본:

- [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/dev/adb_wifi.md)
- [AOSP adb command reference](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md)
- [LADB source](https://github.com/tytydraco/LADB/blob/main/app/src/main/java/com/draco/ladb/utils/ADB.kt)

현재 relay 구현은 위 동작을 독립적으로 새로 작성했으며 LADB/AOSP 코드를 복사·링크하지 않았다.

## 6. Android 버전 호환 계층

### Android 17 이상

- ADB Wi-Fi 2.0 지원 여부를 확인한다.
- 지원 시 서비스 메타데이터와 새 discovery 흐름을 우선 사용한다.
- 지원이 보고되지 않으면 기존 Android 16 경로로 안전하게 폴백한다.

### Android 16

- 기존 `_adb-tls-pairing._tcp` 및 `_adb-tls-connect._tcp` mDNS 흐름을 사용한다.
- 자동 탐지가 실패하면 사용자가 설정 화면에 표시된 포트를 직접 입력할 수 있다.

### One UI

- One UI 버전 문자열은 지원 안내에 사용하되 핵심 코드 분기는 Android API와 실제 기능 탐지로 결정한다.
- 제조사 문자열만 믿고 기능을 활성화하지 않는다.

## 7. ADB relay 보안 전략

### 계획 H1 — 휴대형 USB ADB bridge

1. 브리지가 Fold8의 실제 USB `adbd`에 host로 연결한다.
2. 브리지 `adb` server는 기본 loopback socket을 유지한다.
3. 집 PC는 Tailscale 제한 SSH로 브리지 안의 `adb`를 실행한다.
4. 표준 PC ADB가 필요하면 SSH local forwarding으로 bridge loopback에만 연결한다.
5. `5037`, `5555`와 관리 API를 핫스팟·LAN·공인 인터페이스에 bind하지 않는다.
6. Tailscale node, SSH·Agent와 Android USB ADB RSA를 서로 다른 인증 계층으로 사용한다.

이 경로는 S1·S2의 Android 무선 ADB relay와 별개이며 현재 미구현이다.

### 출고 우선안 S1 — Tailnet 전용 listener

1. 앱은 자기 휴대폰의 무선 ADB connect 포트를 mDNS 또는 수동 입력으로 얻는다.
2. 앱이 인증된 outbound tunnel을 집 PC Gateway로 연다.
3. Gateway가 PC loopback에만 ADB 접속점을 열고 표준 `adb.exe`의 raw TCP를 phone loopback adbd로 전달한다.
4. 휴대폰 일반 Wi-Fi·핫스팟·이동통신 인터페이스에는 relay listener를 열지 않는다.
5. PC Gateway의 `--tailnet` listener는 Tailscale CLI가 반환한 정확한 단일 IPv4만 허용하며 wildcard, LAN, 공인 주소를 거부한다.

현재 PC에서 self-contained Gateway의 `run --tailnet`, pinned-TLS `status --tailnet`, 미인증 relay 폐쇄와 종료 후 포트 폐쇄를 검증했다. Fold8에서 실제 외부망 ADB E2E는 남아 있다.

### 구현 S2 — 인증된 outbound reverse tunnel

현재 기술 스파이크는 이 경로를 구현했다. 휴대폰이 기존 Tailscale 경로 또는 후속 직접 경로로 집 PC Gateway에 outbound TLS 연결을 열고, Gateway는 휴대폰 인증 뒤에만 PC loopback ADB 접속점을 만든다. 이 구조는 Android에 public listener를 만들지 않는다.

### 제한적 진단안 S3 — 전역 TCP ADB

`adb tcpip 5555`처럼 adbd를 모든 인터페이스에 열 수 있는 방식은 초기 기술 확인에만 사용할 수 있다. 다음 조건을 충족하지 않으면 공개 APK에 포함하지 않는다.

- 일반 LAN에서 포트 접근이 차단됨
- 이동통신·핫스팟 인터페이스 노출 없음
- 승인되지 않은 PC 연결 차단
- OFF와 앱 강제종료 후 포트 닫힘

S1이 실패하면 S2를 선택하며, 편의를 위해 S3를 기본 제품 경로로 강행하지 않는다.

## 9. Quick Settings와 서비스

- `TileService`는 화면 표시용 상태를 자체 추측하지 않고 connection 모듈의 단일 상태 원천을 구독한다.
- 사용자 요청으로만 Foreground Service를 시작한다.
- 서비스 알림에는 현재 상태와 `연결 중지` 액션을 제공한다.
- 재부팅 receiver와 자동 시작 작업은 1차 버전에 넣지 않는다.
- 시스템이 VPN 권한을 회수하면 relay를 먼저 닫고 ERROR로 전환한다.

## 10. 키와 저장

| 데이터 | 저장 위치 후보 | 로그 허용 |
|---|---|---|
| Tailscale 노드 키 | libtailscale 공식 저장소·Keystore 연계 | 금지 |
| ADB 개인 키 | Android Keystore로 보호된 앱 저장소 | 금지 |
| relay 허용 PC 신원·지문 | 암호화된 앱 저장소 | 일부 마스킹 |
| 페어링 코드 | 저장하지 않음 | 금지 |
| 진단 상태 | 앱 내부 제한 로그 | 오류 코드만 |
| ADB 명령·파일·화면 | 저장하지 않음 | 금지 |

앱 데이터 백업으로 개인 키가 다른 기기에 복원되지 않도록 Android backup 정책을 검토한다.

Android 시스템의 ADB RSA 승인 키 저장소는 일반 앱이 임의로 열람·삭제할 수 있다고 가정하지 않는다. 앱은 relay 허용 목록만 직접 관리하며 시스템 ADB 승인 전체 취소는 개발자 옵션으로 안내한다.

## 11. PC Helper 후보 구조

### 필수 CLI

- `doctor`: adb, Tailscale, 장치 주소와 포트 검사
- `connect`: 휴대폰 relay에 연결
- `disconnect`: ADB 연결 해제
- `status`: 장치와 세션 상태 출력
- `scrcpy`: 선택 장치로 scrcpy 실행
- `report`: 민감정보를 제거한 진단 보고서 생성
- `register`: QR·6자리 코드로 휴대폰에 이 PC 등록
- `bridge-status`: 브리지 전원·핫스팟·Tailscale·USB·ADB 단계 확인 — 하드웨어 Gate 뒤 후보

### 선택적 데스크톱 UI

- `연결`, `연결 해제`, `scrcpy 열기`, `진단` 버튼
- 장치 상태와 최근 오류
- 관리자 권한 없이 실행
- Windows Defender 예외를 자동 추가하지 않음

PC Helper는 기존 `adb.exe`를 무단 재배포하지 않고 공식 Platform-Tools 경로를 탐색하거나 사용자가 지정하게 하는 방식을 우선 검토한다.

휴대형 브리지 1차 스파이크에서는 Windows Gateway를 즉시 수정하지 않는다. SSH 경로로 end-to-end를 먼저 증명하고 Android Studio·scrcpy가 원격 ADB server를 사용하지 못할 때만 기존 Gateway Core를 활용한 Agent를 설계한다.

### PC 인증 경계

- Tailscale LocalAPI의 접속 소스 신원 조회를 1차 신뢰 기준으로 사용한다.
- 휴대폰은 사용자가 승인한 안정 장치 ID 후보를 relay 허용 목록에 저장한다.
- QR·6자리 코드는 2분·1회용 등록 요청이며 영구 인증 비밀로 사용하지 않는다.
- relay 허용 뒤에도 Android 버전에 맞는 표준 무선 ADB 페어링·TLS 또는 ADB 키 승인을 통과해야 한다.
- 안정 장치 ID의 실제 필드와 노드 키 회전 시 동작은 기술 스파이크에서 확인한다.
- 세부 흐름은 `PC_인증_보안_기획서.md`를 기준으로 한다.

## 13. 기술 스파이크

1차 인증과 2차 raw relay 스파이크는 로컬 자동시험까지 완료했다. 다음 실제기기 스파이크 순서는 다음과 같다.

1. Fold8에 debug APK 설치
2. 앱에 무선 디버깅 connect 포트를 수동 입력
3. Fold8 앱의 localhost adbd socket 접근 확인
4. 인증된 outbound relay session 생성
5. 집 PC `adb connect 127.0.0.1:47157`
6. ADB shell·push/pull·Android Studio·scrcpy 확인
7. mDNS 자동 탐색과 최초 pairing relay UI 추가
8. 일반 Wi-Fi 인터페이스 포트 비노출과 OFF 차단 검사
9. 그 뒤 direct-home-server 외부 listener 또는 Tailscale 공급자 시험

### 통과 기준

- 같은 APK에서 VPN과 ADB 모듈이 충돌 없이 실행
- Fold8에서 자기 ADB 응답 성공
- 집 PC 표준 ADB 연결 성공
- 일반 네트워크 노출 없음
- OFF 후 접속 불가

하나라도 실패하면 제품 UI 구현 전에 원인과 대안을 보고하고 아키텍처를 재승인받는다.

### 휴대형 bridge 스파이크 순서

1. 부품·포트·전원 H-00 검사
2. Raspberry Pi OS Lite headless 부팅
3. Fold8 2.4GHz hotspot과 Pi Tailscale node 연결
4. Fold8 무선 디버깅 OFF + USB 디버깅 ON
5. Pi `adb devices -l`와 1회 RSA 승인
6. 집 PC SSH에서 shell·logcat·합성 파일 SHA-256 왕복
7. USB·핫스팟 분리 차단과 재연결
8. loopback SSH forwarding과 PC 표준 ADB 호환성
9. 성공 증거 뒤에만 Bridge Agent·통합 UI 재승인

상세 예상 결과와 실패 분기는 `휴대형_USB_ADB_브리지_기획서.md` H-00~H-08을 따른다.

## 15. 승인 결과와 후속 기술 게이트

Windows `RoamADB Gateway`, 공급자 분리와 Apache-2.0은 승인됐다. 1차 인증, 2차 투명 TCP relay, 3차 기존 Tailscale 경유 스파이크를 완료했으며 native ADB 공급원은 불필요한 것으로 결정했다.

- Tailscale Android 포크를 기반으로 사용할지
- 후속 내장형 보안망을 현재 외부 Tailscale 경로와 별도 공급자로 결합할지
- `minSdk 36`, Android 17 target 후보를 승인할지
- Android 자동 discovery가 Android 16·17에서 같은 방식으로 동작하는지
- 휴대형 브리지 H-00~H-06 E2E가 Fold8 LTE/5G 이동 상태에서 통과하는지
- SSH forwarding으로 PC 표준 도구를 지원할지 인증 Bridge Agent가 필요한지
